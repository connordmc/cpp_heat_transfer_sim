# Plan: Recreate the Cryogenic Heat-Transfer Simulation as an Interactive Website

## Context

The repo `cpp_heat_transfer_sim` contains a C++ simulation of **heat leak down a wire in a cryogenic dilution refrigerator**. The user wants (a) an analysis of how it works, (b) a list of inaccuracies/bugs and fixes, and (c) a self-contained plan — to be handed to a separate chat building a **separate, new repo** — for recreating it as a website with ANSYS-caliber visualization but a better UI.

Decisions confirmed with the user:
- **Solver runs entirely in the browser** (TypeScript port; no backend; static hosting).
- **Physics stays 1D** (faithful recreation + bug fixes); the UI/visualization gets the ANSYS-grade treatment.
- **Stack:** React + TypeScript + Vite, Three.js for the 3D wire viewport (user had no stack preference; this was recommended and accepted).

> NOTE: This plan's "deliverable" is the handoff document itself. Nothing in the existing C++ repo is modified.

## Part 1 — How the existing simulation works

### Physical problem
A 1.4 m wire runs from a cold load (mixing chamber, x = 0) to room temperature (x = 1.4 m). It is **copper**, except for an **NbTi superconducting segment from x = 0.4–0.6 m**. Seven thermal anchor "plates" sit at x = {0, 0.15, 0.30, 0.45, 0.60, 1.00, 1.40} m with setpoints {load, 0.01, 0.1, 1.0, 4.0, 50, 300} K and max cooling powers {0, 1 mW, 10 mW, 100 mW, 1 W, 10 W, 10 kW} (`src/main.cpp:21-26`). Key engineering questions: where does T cross **9.2 K (NbTi critical temperature)**, what is the heat load into each cryo stage, and how does the transient evolve over 900 s from a uniform 300 K start.

### Numerics
- **PDE:** 1D transient heat conduction, ρ·c_p·∂T/∂t = ∂/∂x(k ∂T/∂x) + q_joule.
- **Grid:** 500 finite-difference nodes, dx ≈ 2.8 mm (`src/main.cpp:15,37`).
- **Time stepping:** Crank-Nicolson, dt = 0.1 s, 9000 steps (`src/main.cpp:73-76`), assembled as sparse A·Tⁿ⁺¹ = B·Tⁿ + G + J∘Tⁿ and solved with Eigen SparseLU (`src/Solver.cpp:127-219`). A ForwardEulerSolver also exists (`src/Solver.cpp:42-123`) but is unused — and would be wildly unstable at dt = 0.1 s (explicit stability limit ≈ 3×10⁻⁵ s for Cu at this dx).
- **Material properties:** temperature-dependent k(T), c_p(T), ρ_elec(T) for Cu and NbTi, loaded from CSVs (`src/MaterialLoad.cpp`) generated by `data_scripts/generate_mats.py` (NIST cryogenic fits, ~4–500 K), linearly interpolated at runtime (`src/TabulatedProperty.cpp`).
- **Boundary/anchor conditions:** right end hard Dirichlet at 300 K; anchor plates are "fixed" nodes with a tanh-smoothed, power-capped controller toward a setpoint (`src/Solver.cpp:166-172`); node 0 treated as a 1 Ω lumped resistor for Joule heating.
- **Source term:** Joule heating q = ρ_e·I² with a finite-difference Jacobian of the source linearized into the matrix (`src/Solver.cpp:146-148, 181-183, 225-237`). Current is set to **0 A** in main, so the shipped run is passive cooldown only.
- **Output:** HDF5 `simulation_output.h5`, 52 snapshots × 500 nodes with dx/dt/plate-index attributes. No C++ visualization; `Python_Sim/PythonSim.py` is a simpler constant-property Python reference that plots T(x,t) line fans and a temperature-colored wire diagram with plate blocks and a 9.2 K annotation — this is the visual language the website should upgrade.
- **No build system** (no CMakeLists/Makefile committed). Dependencies: Eigen, HDF5 C++.

### Verified-correct details worth keeping
- Harmonic-mean interface conductivity **is** used in the Forward Euler solver (`src/Solver.cpp:57-58`) — the right idea, just absent from the CN solver actually used.
- The mysterious `G(i) += 600*R` at the second-to-last node (`src/Solver.cpp:178-180`) is a **correct** Dirichlet elimination (300 K × R from both the implicit and explicit sides), not a bug.
- Snapshot bookkeeping is correct: 51 in-loop saves + 1 final = 52 rows, matching the preallocated HDF5 extent (last row duplicates step 9000).

## Part 2 — Inaccuracies and necessary fixes

Ordered by severity. "Fix" describes both what the C++ would need and what the website port must do instead.

| # | Severity | Issue | Location | Fix |
|---|----------|-------|----------|-----|
| 1 | **Critical (build)** | `main.cpp` constructs Nodes with 4 args but only 3- and 5-arg constructors exist — the project as committed does not compile; and the 3-arg ctor leaves `fixed_temp` uninitialized, so the anchor controller's setpoint is garbage/0 K | `src/main.cpp:69`, `include/Node.hpp:7-8`, `src/Node.cpp:3-12` | Pass the setpoint explicitly; initialize `fixed_temp` in every constructor. Website: setpoint is a first-class plate property. |
| 2 | **Critical (physics)** | In the CN matrix, node 0's row has diagonal 1+2R but **no off-diagonal coupling to node 1** on either A or B — the left end is thermally disconnected and the orphaned 2R term acts as an artificial sink pulling T₀ toward 0 K | `src/Solver.cpp:158-163` | Use a proper one-sided (insulated or resistor-coupled) stencil: couple node 0 to node 1 with −R/+R off-diagonals and a 1+R diagonal (Neumann) or model the lumped resistor explicitly. |
| 3 | **High (physics)** | CN uses node-centered k for the whole row (single R per node, same value on both off-diagonals). No harmonic-mean face conductivity → non-conservative scheme, wrong fluxes at the Cu↔NbTi interface and wherever k(T) varies steeply (it varies by orders of magnitude over 0.01–300 K) | `src/Solver.cpp:150, 183-192` | Conservative finite-volume form: k_face = harmonic mean of neighbor k's; R_left ≠ R_right per row. (Forward Euler already does this — port that idea into CN.) |
| 4 | **High (units)** | Joule heating units inconsistent: `qgen = ρ_e·I²` assumes unit cross-section (comment in `Solver.cpp:13`), but it is then multiplied by `factor = dt/(ρ·c·A·dx)` as if it were total watts per element. Correct element power is P = I²·ρ_e·dx/A (volumetric q''' = I²ρ_e/A²). Off by ~A·dx ≈ 10⁻⁹ — masked only because I = 0 | `src/Solver.cpp:12-14, 147, 169-176` | Define q''' = I²ρ_e/A² and keep everything volumetric; carry the cross-section A (currently hardcoded with π truncated to 3.14159 at `Solver.cpp:128`) as a user parameter. |
| 5 | **Medium (numerics)** | Source-term Jacobian sign appears flipped: A gets +J on the diagonal and the RHS gets +J·Tⁿ, which expands to G(Tⁿ) − J·(Tⁿ⁺¹−Tⁿ), the **opposite** of the Newton/Taylor linearization G(Tⁿ) + J·(Tⁿ⁺¹−Tⁿ). Acts as artificial damping rather than correct linearization | `src/Solver.cpp:181-183, 198` | Use (1+2R−J) on the diagonal with RHS −J·Tⁿ (or simply Picard-iterate properties; at these time scales 1–2 lagged-property iterations suffice). |
| 6 | **Medium (model)** | Anchor-plate controller `smoothing = dx·100·tanh(ΔT/10)` is dimensionally arbitrary (gain depends on grid spacing; max deliverable power is silently 0.28×max_power; the 10 K tanh width is hardcoded) | `src/Solver.cpp:167-168` | Replace with a well-posed power-capped penalty/Robin condition: Q_plate = clamp(G·(T−T_set), −P_max, +P_max) with a physically chosen conductance G, integrated implicitly. |
| 7 | **Medium (UB)** | Property interpolation: if T exactly equals the table's first entry, `lower_bound` returns begin() and `idx = distance−1` underflows `size_t` → out-of-bounds read | `src/TabulatedProperty.cpp:5-15` | Handle `it == begin()`; clamp idx into [0, n−2]. |
| 8 | **Low (robustness)** | Properties silently clamp outside the 4–500 K table range — yet plate setpoints go down to **0.01 K**, far below the data, so the coldest physics is extrapolated flat with no warning | `src/TabulatedProperty.cpp:6-7`, data range from `data_scripts/generate_mats.py` | Extend fits below 4 K where models allow (c_p → Debye T³ behavior matters at mK temperatures) or at minimum surface a warning; website should show an "out of property range" indicator. |
| 9 | **Low (model gap)** | NbTi superconducting transition is not modeled: ρ_e(T) is loaded but nothing zeroes resistivity below T_c = 9.2 K or handles quench; with I = 0 in main, Joule heating never exercises any of this | `src/main.cpp:75`, solver generally | Website: ρ_e = 0 below 9.2 K for NbTi (with optional current-sharing/quench model), and current as a live UI parameter. |
| 10 | **Low (data)** | Cu thermal-conductivity low-T clamp branch has a typo: `f*T*sqrt(4)` should be `f*4*sqrt(4)`, so the "constant below 4 K" value still varies (incorrectly) with T | `data_scripts/generate_mats.py:18` | Implement as a clean clamp `k_Cu(max(T, 4))`. |
| 11 | **Low (data)** | `nbti_specific_heat` returns `None` at exactly T = 20, 50, or 175 K (piecewise conditions use strict `<`/`>` with gaps at the boundaries) — crashes CSV generation if the sample grid lands on those values | `data_scripts/generate_mats.py:72-81` | Make piecewise boundaries inclusive (`<=`). |
| 12 | **Low (cosmetic)** | Progress ETA divides by `step` = 0 on the first iteration (prints inf); `length` initialized with a float literal `0.0f` into a double; unused `resistor_length`; dead `step_dynamic` computes a stability dt that is never applied | `src/main.cpp:116-121,30`, `src/Solver.cpp:81-123,141` | Tidy in any C++ cleanup; not ported. |

## Part 3 — Website recreation plan (handoff to new repo)

**Project: "CryoWire" — interactive cryogenic heat-transfer simulator.** Static-hosted web app, solver runs entirely in-browser in a Web Worker, setup → solve → results workflow at ANSYS caliber with a modern UI. This section is self-contained for the implementing chat; the only external references it needs are the ground-truth files listed at the end.

### 3.0 Physical problem recap (no other context needed)
- Wire, L = 1.4 m, circular cross-section, diameter 1 mm → A = π·(5e-4)² ≈ 7.854e-7 m².
- OFHC copper (ρ = 8960 kg/m³) everywhere except NbTi (ρ = 6000 kg/m³) from x = 0.4–0.6 m.
- Seven anchor plates at x = {0, 0.15, 0.30, 0.45, 0.60, 1.00, 1.40} m, setpoints {load(0), 0.01, 0.1, 1.0, 4.0, 50, 300} K, max cooling powers {0, 1e-3, 1e-2, 0.1, 1, 10, 1e4} W. Left end insulated (the x=0 "load" plate has P_max = 0); right end Dirichlet 300 K.
- PDE: ρ·c_p(T)·∂T/∂t = ∂/∂x(k(T)·∂T/∂x) + q''' with Joule heating from current I (default 0 A). NbTi superconducts below T_c = 9.2 K (ρ_e = 0).
- Default run: T(x,0) = 300 K, simulate 900 s, 500 nodes.
- Key results: T(x,t); x where T crosses 9.2 K; heat extracted by each plate vs t; heat flux q(x) = −kA·∂T/∂x; energy balance.
- **Fix, do not replicate**, the bugs in Part 2 (especially #2–#6).

### 3.3 Materials — embed NIST fits as TS functions (port of `data_scripts/generate_mats.py`; no CSVs)

`materials.ts` exports `{ name, density, k(T), cp(T), rhoE(T) }` per material. Exact formulas (verified against the repo):

- **Cu k(T)** — NIST OFHC log-polynomial: `log10(k) = (a + c√T + eT + gT√T + iT²)/(1 + b√T + dT + fT√T + hT²)` with a=1.8743, b=−0.41538, c=−0.6018, d=0.13294, e=0.26426, f=−0.0219, g=−0.051276, h=0.0014871, i=0.003723. Below 4 K: clean clamp `k(max(T,4))` (fixes bug #10).
- **Cu c_p(T)** (J/kg·K): T < 4 K → Sommerfeld/Debye `0.0108·T + 0.00076·T³`; T ≥ 4 K → `log10(cp) = Σ coefₙ·(log10 T)ⁿ`, coefs [−1.91844, −0.15973, 8.61013, −18.996, 21.9661, −12.7328, 3.54322, −0.3797].
- **Cu ρ_e(T)** — Bloch–Grüneisen, RRR = 50: ρ₀ = 15.53e-9/RRR, θ_D = 343 K, ρ_ph(T) = 15.53e-9·(T/θ_D)⁵·J(θ_D/T)/[(273/θ_D)⁵·J(θ_D/273)], J(u) = ∫₀ᵘ x⁵/((eˣ−1)(1−e⁻ˣ))dx. Implementation: tabulate once at module load on a 256-pt log-spaced grid over [0.5, 500] K via composite Simpson, interpolate in log T (avoids per-call quadrature; matches scipy.quad to <0.1%).
- **NbTi c_p(T)** (J/kg·K), piecewise polynomials with **inclusive** boundaries (fixes bug #11): T<20 → `0.165714286·T + 0.0029·T³`; 20≤T<50, 50≤T<175, T≥175 → the three quartics from `generate_mats.py:77-81` verbatim.
- **NbTi k(T)** (W/m·K): the three piecewise polynomials from `generate_mats.py:85-89` verbatim (T≤10 cubic, 10<T≤100 sextic, T>100 cubic).
- **NbTi ρ_e(T)**: `5.6e-7 · ½(1 + tanh((T − 9.2)/w))`, w default 0.05 K — smooth superconducting transition keeps the nonlinear iteration differentiable when I > 0; w→0 recovers the sharp step.

All properties declare a `validRange`; out-of-range input is clamped **and flagged** in diagnostics (UI warning chip) — fixes the silent clamping (#8). Golden-value tests: ~6 reference values per property computed from the Python script (e.g. k_Cu(300) ≈ 398–401, cp_Cu(300) ≈ 385).

### 3.4 Solver core

**Data model (`types.ts`):**
```ts
interface SimConfig {
  length: number; numNodes: number; area: number;
  segments: { materialId: 'cu'|'nbti'; x0: number; x1: number }[];
  plates: Plate[];
  rightBC: { type:'dirichlet'; T:number } | { type:'adiabatic' };
  leftBC: { type:'adiabatic' };
  current: number;                          // A
  initial: { type:'uniform'; T:number } | { type:'linearBetweenPlates' };
  tEnd: number;
  solver: SolverSettings;
}
interface Plate { id:string; name:string; x:number; Tset:number; Pmax:number;
                  conductance:number /* G, W/K */; enabled:boolean; }
interface SolverSettings {
  dtInit:number; dtMin:number; dtMax:number;      // 0.1 / 1e-4 / 1.0 s
  maxRelDeltaT:number;                            // 0.05 step-size target
  picardTol:number; picardMaxIter:number;         // 1e-8, 25
  snapshotInterval:number;                        // sim-seconds per stored frame
}
```

**Spatial scheme — conservative finite volume, harmonic-mean faces (fixes #2, #3):** nodes at x_i = i·dx; control volumes V_i = A·dx (A·dx/2 at ends). Face conductivity `kf = 2·k_i·k_{i+1}/(k_i + k_{i+1})`, face conductance `Cf = kf·A/dx` (W/K). Semi-discrete: `ρ_i c_i V_i dT_i/dt = Cf_{i+½}(T_{i+1}−T_i) − Cf_{i−½}(T_i−T_{i−1}) + Q_joule,i + Q_plate,i`. Node 0 has only its right face (insulated left — fixes the disconnected node 0). Node N−1: Dirichlet row (T = 300) with proper coupling into row N−2; the 300 K stage's "power" is reported as the actual boundary flux in diagnostics.

**Joule heating (fixes #4):** per-element power `Q_joule,i = I²·ρ_e(T_i)·Δx_i / A` W (element resistance ρ_e·Δx/A); volumetric q''' = I²ρ_e/A². Zero on NbTi below 9.2 K via the smooth ρ_e(T) — gives a self-consistent quench-heating loop above T_c.

**Plate controller (fixes #1, #5, #6):** power-capped Newton cooling at each plate node: `Q_plate = −Pmax·tanh(G·(T − Tset)/Pmax)`. Dimensionally correct (G in W/K is a real anchor conductance, user-editable; default `G = 100·Pmax/max(Tset, 0.01)` so it pins within ~1% of setpoint before saturating at exactly Pmax). Treated implicitly with the correct Newton linearization `Q(Tⁿ⁺¹) ≈ Q(T*) + Q′(T*)(Tⁿ⁺¹−T*)`; Q′ = −G·sech²(·) ≤ 0 adds to the matrix diagonal → unconditionally stabilizing (fixes the flipped Jacobian sign).

**Time integration — adaptive Crank-Nicolson + Picard:** the 300 K → mK cooldown is stiff (c_p drops ~5 decades), so fixed-property dt = 0.1 s CN is neither accurate nor robust. Per macro step: Picard-iterate (≤25): evaluate k, c_p, ρ_e, Q at the CN ½-state ½(Tⁿ + T*); assemble tridiagonal `(M/dt + ½K + ½D)Tⁿ⁺¹ = (M/dt − ½K − ½D)Tⁿ + S`; Thomas solve (preallocated Float64Array scratch, ~3N flops); converge on max rel ΔT < tol. Step control: halve dt on non-convergence or rel change > 5% (floor dtMin); grow ×1.5 when easy (cap dtMax); retry at smaller dt if any T ≤ 0. Optional Phase-3 flag: TR-BDF2 (L-stable, kills CN ringing on the initial shock). Also `steadyState.ts`: damped Newton on the steady equations for an instant steady-state preview while dragging parameters. Budget: 500 nodes × ~5 iters × ~3000 steps ≈ 10⁷ flops per full 900 s transient — a few ms; full re-solve on every parameter change is fine.

**Diagnostics per snapshot:** face fluxes (W); per-plate extracted power; 9.2 K crossing x-positions (linear interpolation, may be multiple); energy budget `dE/dt vs ΣQ − boundary flux` with cumulative relative residual; property-clamp warning count.

### 3.5 Web Worker architecture

Worker owns the stepper and full history; main thread never blocks.

```ts
// main → worker
type ToWorker =
  | { type:'configure'; config:SimConfig }      // reset + re-solve from t=0
  | { type:'run' } | { type:'pause' } | { type:'reset' }
  | { type:'runSteady' }                        // steady preview solve
  | { type:'setSpeed'; simSecondsPerWallSecond:number };
// worker → main
type FromWorker =
  | { type:'ready' }
  | { type:'configAccepted'; grid:{ x:Float64Array; materialIndex:Uint8Array } }
  | { type:'batch'; t0Index:number; times:Float64Array;
      temps:ArrayBuffer; platePowers:ArrayBuffer;          // Float32, TRANSFERRED
      crossings:{ t:number; xs:number[] }[]; energyResidual:Float32Array }
  | { type:'progress'; simTime:number; dt:number; picardIters:number }
  | { type:'done'; totalSnapshots:number }
  | { type:'steadyResult'; temps:ArrayBuffer }
  | { type:'warning'; kind:'clamp'|'dtFloor'|'nonconverged'; detail:string }
  | { type:'error'; message:string };
```
Snapshots batched (~every 16 ms wall or 25 frames) with transferable ArrayBuffers (Float32 for display; Float64 retained worker-side). Main-thread mirror: one preallocated `Float32Array(maxSnaps × N)` (900 s @ 1 s interval ≈ 1.8 MB) — scrubbing reads it directly, zero worker round-trips. `simClient.ts` wraps this in a typed API, writes via zustand transient setters, debounces `configure` at 100 ms during drags, and fires `runSteady` immediately for the live preview overlay.
